Dear Riverlane team,

I am applying for the Software Engineer (Open Source) role because Deltakit is the kind of software I have spent the last two years building: an open-source, user-facing tool that a small, highly technical community depends on, where the hard part is not the feature but whether a researcher can pick it up and trust it.

Most of my open-source work has been exactly that translation problem. I spent an LFX mentorship on Microcks CLI v2, a CNCF project, moving API contract testing out of CI and into the developer inner loop — running a test used to cost a server, credentials and a specification import, so teams found out about breakages a pull request too late. It now runs against an ephemeral container in one command. I designed the output around how people actually debug: failures resolve to the exact line of the specification that drifted, and exit codes are classified so the scripts wrapping the CLI can act on them. Then I extended it into VS Code, deliberately CLI-first so the editor never becomes a second control plane.

I do the same upstream in Kubernetes, where I am Documentation Lead for the v1.38 release, directing five shadows to a release day that does not move. Before that I rebuilt the generator behind the API reference every Kubernetes user reads — cutting generation from hours to minutes, and catching a silent correctness bug where the reference had been dropping enum values because the upstream spec omitted them. That work is mostly listening: reading what users report, finding the real defect underneath it, and shipping something a maintainer will accept. I also review other people's contributions, which is where most of the community work actually happens.
